# Mayous

マウスの**同時押し**をショートカットに変える Windows 常駐ツール。C + Win32 API のみ、依存 DLL なしの単一 exe。

| 操作 | 既定の動作 |
|---|---|
| 右クリックを押しながら左クリック | Windows キー |
| 左クリックを押しながら右クリック | Alt+Tab |
| 右クリックを押しながらホイール | 左右スクロール（水平ホイール） |

割り当ては**設定ウィンドウ**から変更できます。一覧から機能を選ぶほか、
`ctrl+shift+t` のような任意のキーコンボを直接入力することもできます。

---

## 使い方

1. `mayous.exe` を好きな場所に置いて実行するだけ。インストーラ不要。
2. 初回起動時に同じフォルダへ `mayous.ini` が作られ、タスクトレイに常駐します。
3. トレイアイコンを**ダブルクリック**すると設定ウィンドウが開きます。
   シングルクリック（左右どちらでも）でメニュー：

   - **設定...** … 設定ウィンドウを開く
   - **有効** … 全機能の ON/OFF
   - **Windows 起動時に実行** … スタートアップ登録（HKCU の Run キー）
   - **設定ファイルを開く** … `mayous.ini` をメモ帳で開く
   - **設定を再読み込み** … 手で編集した内容を即反映
   - **割り当ての確認** … 現在の割り当て一覧を表示
   - **終了**

### 設定ウィンドウ

8 つの組み合わせそれぞれに、ドロップダウンから機能を割り当てます。
ウィンドウ操作／スクロール／ブラウザ・タブ／編集／メディアなど約 40 種類の
プリセットが入っており、**一覧に無い操作は `ctrl+shift+t` のように直接入力**できます。

長押し判定・ドラッグ判定・除外アプリもここで設定できます。
**OK / 適用を押した時点で即座に反映**されます（再起動不要）。

`mayous.exe --exit` で外部から終了させられます（アンインストールや入れ替え用）。

exe を Program Files など書き込めない場所に置いた場合、設定は
`%APPDATA%\Mayous\mayous.ini` に作られます。それ以外はポータブル動作です。

## 設定

```ini
[General]
Enabled=1
DragThreshold=0          ; 押下を「本物の押下」に昇格させるドラッグ距離(px)。0=システム設定
LeftHoldTimeoutMs=200    ; 左の長押し救済(ms)。0=無効
RightHoldTimeoutMs=0     ; 右の長押し救済(ms)。0=無効
SuspendOnFullscreen=1    ; フルスクリーンのアプリが前面なら自動停止

[Chords]
RightThenLeft=win
RightThenMiddle=none
RightThenWheelUp=hwheel_right
RightThenWheelDown=hwheel_left
LeftThenRight=alttab
LeftThenMiddle=none
LeftThenWheelUp=none
LeftThenWheelDown=none

[Exclude]
Processes=               ; 前面のあいだ全機能を止める exe 名。カンマ区切り
```

### 割り当てに書ける値

設定ウィンドウを使わず ini を直接編集することもできます。

| 値 | 意味 |
|---|---|
| `none` | 何もしない。**そのボタンを一切乗っ取らない** |
| `hwheel_left` / `hwheel_right` | 水平ホイール |
| `win` / `alttab` / `alttab_back` | よく使うものの別名 |
| `ctrl+w`, `alt+left`, `win+d`, `f5` … | 任意のキーコンボ |

修飾子は `ctrl` `alt` `shift` `win`。キーは `a`〜`z` `0`〜`9` `f1`〜`f24`
`tab` `enter` `esc` `space` `backspace` `delete` `insert` `home` `end`
`pageup` `pagedown` `left` `right` `up` `down` `apps` `printscreen`
`volumeup` `volumedown` `volumemute` `medianext` `mediaprev` `mediaplay`
`browserback` `browserfwd`。

左右スクロールの向きを逆にしたいときは `hwheel_left` と `hwheel_right` を入れ替えてください。

**あるボタンの割り当てを全部 `none` にすると、そのボタンには一切手を触れません。**
「左押しながら右」が不要なら `LeftThenRight` 等を `none` にしておくと、
左クリックは完全に素通しになり副作用がゼロになります。

## 仕組み

同時押しの本質的な難所は「先に押されたボタンのクリックをどう殺すか」です。
押下の瞬間には、それが修飾キー役なのか通常のクリックなのか判別できません。
そこで **押下を飲み込んで保留し、その後に起きたことで運命を決めます**。

```
 PS_IDLE ──押下(フックで握り潰す)──> PS_PENDING
                                        │
        相方ボタン / ホイールが来た ────┼──> PS_CONSUMED
                                        │      同時押し成立。離上も殺す
        しきい値を超えて移動した ───────┼──> PS_PASSTHRU
        長押しタイムアウト ─────────────┘      本物の押下を合成注入して以降素通し
                                        │      (ドラッグ・長押しの救済)
        何も起きずに離された ───────────┴──> DOWN+UP を合成注入
                                               通常クリックとして成立させる
```

この結果、通常の右クリックは**押した瞬間ではなく離した瞬間**に発火します。
素早いクリックなら体感できませんが、原理上そうなります。

自分が `SendInput` したイベントには専用のタグ（`dwExtraInfo`）を付け、
フック側で無条件に素通しさせることで再入と無限ループを断ち切っています。

### なぜフックの中で SendInput してはいけないのか

低レベルフックのコールバックの中で `SendInput` を呼ぶと、**実測で 250〜450ms
戻ってこない**。注入した入力を処理するのは、今まさにこちらの応答を待っている
当のスレッドだからである。その間に Windows は `LowLevelHooksTimeout` で
フックを見限り、**握り潰したはずのイベントをアプリへ配送してしまう**。

結果、押下だけが消えて離上が届く／クリックが二重になる、といった収拾のつかない
壊れ方をする。実測ログ:

```
137076375  evt 0x0201 (左押下)  -> SWALLOW
137076468  evt 0x0202 (左離上)  ハンドラ開始
137076687  APP  LEFT UP         <<< 生の離上がアプリに漏れた
137076921  inject CLICK         453ms 後にようやく完了。もう手遅れ
```

そこで**フックの中では「握り潰すか否か」の判断だけを行い、実際の注入は
キューに積んでメッセージループへ回している**。フックから戻った直後に
処理されるので、実測でフック→アプリ到達まで約 16ms に収まる。

### GetAsyncKeyState は握り潰した押下を見ていない

押下をフックで握り潰すと、その押下は **OS のキー状態に一切記録されない**。
つまり保留中は `GetAsyncKeyState(VK_RBUTTON)` が、ユーザーが実際に押していても
「離されている」と答える。

これを知らずに「2 秒経っても押されていない＝取りこぼした残骸」として状態を
破棄していたため、**右ボタンを 2 秒以上押していると同時押しが効かなくなり、
さらに離上だけがアプリに素通しして両ボタンの挙動が壊れる**という不具合になっていた。

現在は、自分で押下を注入した `PS_PASSTHRU` のときだけ `GetAsyncKeyState` を
信用し、保留中は判定に使っていない（押しっぱなしは正当な状態なので）。
取りこぼしの回復は次の 3 段構えで行う:

- **押下時の辻褄合わせ** … 前回が決着していないボタンに押下が来たら、そこで清算する。
  「押下だけがアプリに届いて離上は握り潰される」＝ボタンが押されっぱなし、という
  最悪の事故を構造的に防ぐ最後の砦。
- **デスクトップ切替の検出** … UAC のセキュアデスクトップやロック画面へ移ると、
  その間の離上は届かない。`EVENT_SYSTEM_DESKTOPSWITCH` で検出して状態を捨てる。
- **60 秒の保険** … それでも残った場合のみ畳む。

### なぜホイール注入だけ子プロセスなのか

Windows は **`WH_MOUSE_LL` を保持しているプロセスからのホイール注入を黙って捨てます**。
`SendInput` は `1` を返し `GetLastError` も `0` なのに、イベントは自分のフックにすら現れません。
実測（`tools/hwheel_test.c`）：

| 条件 | 結果 |
|---|---|
| フック保持 + メインスレッドから HWHEEL | 消滅 |
| フック保持 + 別スレッドから HWHEEL | 消滅（プロセス単位の制約） |
| フック保持 + 縦ホイール | 消滅（水平に限らない） |
| フックを外した直後に HWHEEL | 通る |

そこで **フックを一切持たない注入専用の子プロセス**を、同じ exe の `--wheel-agent`
モードとして起動しています。本物のチルトホイールと完全に同じ経路を通るので、
水平スクロールに対応したアプリなら等しく反応します。
子プロセスは親の終了を待って自動的に道連れで終わります（孤児にならない）。

一時的にフックを外して注入する案は、その隙間に生のホイールが素通ししてしまい、
連続スクロール中に縦スクロールが漏れるため採用していません。

## 既知の制限

- **管理者権限で動いているウィンドウの上では効きません。** UIPI により、
  昇格していないプロセスのフックはそこに届きません。必要なら mayous 自身を
  管理者として実行してください（既定は `asInvoker`。常駐物を常時昇格させる
  不利益のほうが大きいと判断しています）。
- **UAC の昇格画面や Ctrl+Alt+Del の画面（セキュアデスクトップ）では動作しません。** OS の仕様です。
- **ゲームには使わないでください。** アンチチートが低レベルフックを不正ツールと
  みなす可能性があります。既定で `SuspendOnFullscreen=1`（フルスクリーン時は自動停止）に
  してありますが、ボーダーレスウィンドウのゲームなどは `[Exclude]` に exe 名を明記してください。
- 通常の右クリックは**離した瞬間**に発火します（上記「仕組み」）。
- 右ドラッグは `DragThreshold`（既定 8px 前後）を超えるまで押下が世に出ません。
  3D ビューの回転など、最初の数ピクセルが失われます。
- 左ボタンは `LeftHoldTimeoutMs`（既定 200ms）で長押しに切り替わるため、
  Alt+Tab を出すには**左を押してから 200ms 以内に右**を押す必要があります。
  長めにしたい場合はこの値を上げてください（そのぶん左の長押し反応が鈍ります）。
- **マウスの左右ボタン入れ替え設定（SwapMouseButton）には未対応**です。
- 全画面判定は「ウィンドウ矩形がモニタ矩形と一致するか」で行うため、
  タスクバーを自動的に隠す設定では最大化ウィンドウを全画面と誤判定することがあります。

## ビルド

MinGW-w64（GCC）が必要です。

```
winget install BrechtSanders.WinLibs.POSIX.UCRT
build.bat
```

`build\mayous.exe` ができます。`-static` でリンクしているので、
配布先に libgcc 等の DLL は不要です（依存は Windows 標準の DLL のみ）。

```
build.bat debug     デバッグビルド。%TEMP%\mayous_debug.log にトレースを吐く
```

アイコンは `tools\make_icons.ps1` が生成します（外部素材なし）。
`res\mayous.ico` が無ければ `build.bat` が自動的に呼びます。

> MinGW は非共有リンク時に `default-manifest.o` を必ず巻き込むため、`.rc` に
> 自前マニフェストを入れると ld が `multiple non-default manifests` で落ちます。
> `build.bat` は自前マニフェストを `default-manifest.o` という名前で作り、
> `-B` で探索パスの先頭に置いて本家を差し替えています。

## テスト

```
powershell -ExecutionPolicy Bypass -File tools\run_tests.ps1
```

`probe.exe` を **mayous より先に**起動することで、フック鎖の下流
（＝アプリから見える位置）に観測点を置き、`SendInput` で実際のマウス操作を
注入して「何が握り潰され、何が合成されたか」をログで検証します。

検証項目：単独右クリックの遅延合成 / 右+左 / 左+右 / 右+ホイール /
右ドラッグ昇格 / 左長押し昇格 / 未割り当てボタンの素通し。

```
powershell -ExecutionPolicy Bypass -File tools\stress.ps1
```

状態機械の総当たり検証。**本物のウィンドウ**（`target.exe`）を相手に
14 通りの操作列を注入し、アプリ側で**押下と離上が釣り合っているか**を検証します。
釣り合いが崩れる＝ボタンが押されっぱなし＝全クリックが壊れる、という
最悪の壊れ方を直接検出できます。

> `probe.exe` はフック鎖の中に居るため、OS がフックを呼ぶ順番次第で上流にも
> 下流にもなり得ます（実測で入れ替わることを確認）。並び順に依存しない
> 計測が必要な場面では `target.exe` を使ってください。

## ファイル構成

```
src/common.h     共通定義（設定構造体・コード定義）
src/main.c       常駐本体。トレイ、フック設置、前面ウィンドウ監視
src/chord.c      同時押し判定の中核。状態機械とイベント抹殺・合成注入
src/config.c     mayous.ini の読み込みとキーコンボ解析
src/agent.c      ホイール注入専用の子プロセス
src/settings.c   設定ウィンドウ(コントロールを直接生成)
res/             アイコン、マニフェスト、バージョン情報
tools/           アイコン生成、テストハーネス
                 probe.c  … フック鎖に入って観測する
                 target.c … 本物のウィンドウとしてアプリ視点を記録する
```
